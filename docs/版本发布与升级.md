# 版本发布与升级

## 1. 版本事实来源

项目采用 Semantic Versioning，根目录 `VERSION` 是版本号唯一事实来源，格式为 `主版本.次版本.修订版本`，例如 `0.2.1`。Git 标签必须为相同版本加 `v` 前缀，例如 `v0.2.1`。

- 修订版本：兼容性缺陷修复，不改变设备接入契约。
- 次版本：向后兼容的新功能、接口或数据库字段。
- 主版本：存在明确的不兼容变更，需要独立迁移方案。

所有变化先写入 `CHANGELOG.md` 的 `Unreleased`，发布时移动到对应版本标题。禁止覆盖已经发布的版本号或重新推送同名镜像。

## 2. Git 分支与审查

- `main` 始终保持可发布。
- 功能和修复从 `main` 创建短期分支，通过 Pull Request 合并。
- Pull Request 必须通过后端测试、Alembic 检查、前端构建、发布工具测试和 Windows PowerShell 解析。
- `deploy/.env`、`backend/.env`、发布 ZIP、日志、备份和 Docker 数据卷禁止进入 Git。

GitHub 仓库建议设为私有，并为 `main` 启用分支保护：要求 Pull Request、要求 `CI` 全部通过、禁止强制推送和直接删除分支。

## 3. 发布

1. 修改 `VERSION`。
2. 更新 `CHANGELOG.md`。
3. 合并发布 Pull Request。
4. 在 `main` 对应提交创建并推送标签：

```powershell
$version = (Get-Content -Raw VERSION).Trim()
git tag -a "v$version" -m "Release v$version"
git push origin "v$version"
```

`.github/workflows/release.yml` 会验证标签与 `VERSION` 一致，然后：

1. 运行数据库迁移检查、后端测试、管理工具测试和前端构建。
2. 构建并推送 `ghcr.io/<owner>/robots-system-{backend,pm,om}:vX.Y.Z`。
3. 生成较小的 `registry` 安装包和包含全部镜像的 `offline` 安装包。
4. 为两个 ZIP 生成 SHA-256。
5. 创建 GitHub Release 并上传四个文件。

生产部署只引用精确的 `vX.Y.Z` 镜像。`latest` 仅用于本机源码构建和离线包内部兼容，不作为联网部署版本。

## 4. 首次安装

目标 Windows 电脑只需安装并启动 Docker Desktop。下载对应 GitHub Release 的 `registry` 包和 `.sha256` 文件并校验。若 GHCR 包保持私有，先使用具有 `read:packages` 权限的只读 Token 登录一次：

```powershell
$token | docker login ghcr.io -u <github-user> --password-stdin
```

不要把 Token 写入脚本或 `.env`。Docker Desktop 使用系统凭据存储保存登录信息。

解压发布包后，以管理员身份运行 `install.cmd`。发布包安装状态保存在：

```text
C:\ProgramData\RobotsSystem\
  deploy.env            # 随机密钥，只允许部署管理员读取
  release.env           # 当前精确镜像版本
  installed-version     # 当前健康版本
  active-release-path   # 当前管理工具目录
  backups\              # 升级前数据库备份
  install.log           # 安装与升级日志
```

项目数据仍保存在固定名称的 Docker 卷中，不依赖发布包解压目录。

## 5. 在线升级

1. 从 GitHub Release 下载新版本 `registry` ZIP 和 `.sha256`。
2. 解压到新的版本目录，不需要覆盖旧目录。
3. 运行新目录的 `install.cmd`。

安装器会校验发布清单，读取 `C:\ProgramData\RobotsSystem\deploy.env`，在版本变化时先导出 PostgreSQL 备份，再拉取精确版本镜像并执行 Alembic 迁移。只有 PostgreSQL、Redis、后端、PM、O&M 和三个 HTTP 检查全部健康后，才更新 `installed-version`。

镜像拉取失败不会停止旧容器。新应用启动或健康检查失败时，安装器尝试恢复上一版镜像配置；升级前数据库备份始终保留。数据库模式回退不是自动操作，必须由管理员在停机状态下显式恢复备份。

## 6. 离线升级

离线现场使用同一 GitHub Release 中的 `offline` 包。流程与在线升级相同，但安装器从包内 `images.tar` 加载镜像，不连接 GHCR。离线包较大，适合网络受限或需要固定介质归档的现场。

## 7. 数据库迁移规则

- 每个模型变化必须包含 Alembic migration。
- 常规次版本采用 expand/contract：先增加兼容字段或表，再在后续主版本移除旧结构。
- 同一发布中不得同时删除旧字段并要求旧应用回滚。
- destructive migration 必须单独备份、维护窗口和人工恢复演练，不能依赖自动应用回滚。
- 发布前必须执行 `alembic upgrade head` 和 `alembic check`。

## 8. GitHub 权限

- Actions 使用仓库自带 `GITHUB_TOKEN` 写入 GHCR 和 GitHub Release，不保存长期发布 Token。
- 部署机只使用 `read:packages` Token，不授予源码写入或包删除权限。
- 为 GitHub 账号开启双因素认证，限制仓库管理员数量。
- 发布标签和 Release 不得静默替换；发现问题应发布新的修订版本。
