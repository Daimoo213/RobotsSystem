# 多设备产能调度上下文快照

更新日期：2026-07-31

## 本轮目标

将施工任务从单设备派发改为基于真实设备产能的多设备协同调度。平台先计算满足交付量和计划窗口所需的设备类型与数量，再把任务拆成带独立工作配额的执行单元；机器人仍只执行自己收到的单元，不实现 ROS、导航或本地安全控制。

## 已确认事实

- 现有 `MissionExecution` 的活动任务唯一索引和调度器单次 `allocate()` 调用，只允许一项任务分给一台设备。
- 当前设备登记只含工序能力，没有可审计的单位产能。因此不能从铲斗容量、速度或前端数据猜测每小时工作量。
- 技术方案要求集中式调度、DAG、优先级和市场机制；多设备资源规划是这些能力缺失的上层编排。
- 当前真实任务 `T-B69CE7A0` 的交付量为 `500 ㎡`，计划窗口为 `2026-07-31 08:00–10:00 UTC`；已接入设备尚无真实产能登记，因此任务保持 `waiting_capacity / no_valid_capacity_device`，不得虚构设备数量或完成时间。

## 本轮契约

1. 设备网关注册时可登记有来源、证据、上报时间和有效期的单位产能；无有效产能记录的设备不参加工作量覆盖计算。
2. 一项任务包含一个或多个资源需求；每个需求有能力编码、工作量、单位和是否为完成门槛。
3. 调度器用剩余交付量除以可用工时得到需求产能，在在线、空闲、低电量、工序/点位兼容和协议约束后选择实际设备组合。
4. 一台设备同一时间最多一个执行单元；一项任务可有多个执行单元。每个单元下发自己的工作配额，任务完成量只汇总真实遥测。
5. 暂无完整资源包时保持等待并重算；设备失败、取消、离线或产能变化后对剩余工作量重规划。不得重复下发总工作量或把单台失败直接写成业务任务失败。

## 已验证

- 迁移已实际升级至 `20260731_15`；旧任务没有被补写虚构产能、执行单元或完成量。
- 设备注册契约、任务资源计划、命令负载和执行遥测聚合通过后端回归测试和运行中 OpenAPI 核验。
- PM 任务详情的资源计划与执行单元数据形状已通过 TypeScript/生产构建核验；登录态视觉复验仍由已授权操作员完成。

## 本轮收尾记录

- 资源规划器的设备兼容性已改为按资源需求自身的 `capability_code` 判断；辅助运输、吊装等设备不再被任务主工序错误排除。
- 已增加回归测试：异构设备共同覆盖多角色任务，以及一个执行单元完成后只聚合任务进度、不会提前完成业务任务。
- PM 未登录页面已完成截图检查；当前自动化会话无 PM 授权，未尝试读取、使用或伪造登录凭据，因此资源计划详情仍需由已授权操作员做一次视觉复验。
